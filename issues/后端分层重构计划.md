# 后端分层重构计划

本计划旨在将现有的后端架构重构为清晰的分层结构（Controller -> Service -> DAL），以提高代码的可维护性、可扩展性和可测试性。重构将采用渐进式的“绞杀者无花果”模式，从用户模块开始，逐个模块进行改造。

## 第一阶段：以用户模块为样板

### **第一步：打地基 - 创建新目录和基础类型**

1.  **创建目录**:
    *   在项目根目录 `pdfAno-ek/` 下，创建 `services/` 目录，用于存放业务逻辑。
    *   创建 `dal/` 目录，用于存放数据访问逻辑。
    *   创建 `models/` 目录，，用于存放数据传输对象 (Data Transfer Objects)。
    *   **预期结果**: 项目根目录下出现 `services/`, `dal/` 目录，以及 `models/` 目录。

2.  **创建通用响应类型**:
    *   **原子操作**: 在 `models/` 下创建 `api.ts` 文件。
    *   **逻辑概要**: 定义一个通用的 API 响应体 `ApiResponse<T>`，包含 `success`, `data`, `message`, `error` 等字段，以后所有 API 都用这个结构返回，保证统一性。
    *   **预期结果**: 创建 `models/api.ts` 文件并定义好 `ApiResponse<T>` 类型。

### **第二步：重构数据访问层 (DAL)**

1.  **创建 UserRepository**:
    *   **原子操作**: 在 `dal/` 目录下创建 `userRepository.ts` 文件。
    *   **逻辑概要**: 将目前散落在 `app/api/admin/users/**/route.ts` 中所有关于用户表的 `supabase` 操作（增、删、改、查列表、查单个）全部迁移到这个文件中，并封装成独立的函数，例如：
        *   `findMany()`: 获取用户列表。
        *   `findById(id)`: 根据 ID 获取单个用户。
        *   `create(userData)`: 创建新用户。
        *   `update(id, userData)`: 更新用户信息。
        *   `remove(id)`: 删除用户。
        这些函数只负责跟数据库打交道，不包含任何业务逻辑。
    *   **预期结果**: `userRepository.ts` 创建完成，包含所有对用户表的原子化数据库操作。

### **第三步：重构业务逻辑层 (Service)**

1.  **创建 UserService**:
    *   **原子操作**: 在 `services/` 目录下创建 `userService.ts` 文件。
    *   **逻辑概要**:
        *   创建 `UserService`，它会调用 `UserRepository` 中的函数来获取和操作数据。
        *   将原来 `route.ts` 中的业务逻辑（如数据校验、组合多个数据源、复杂的计算等）都搬到 `UserService` 中。例如，`createUser` 方法可能需要先检查邮箱是否已存在，这就是业务逻辑。
        *   `UserService` 不应该知道任何关于 `Request` 和 `Response` 的事，它只负责处理纯粹的业务数据。
    *   **预期结果**: `userService.ts` 创建完成，封装了所有与用户相关的业务逻辑。

### **第四步：定义数据传输对象 (DTO)**

1.  **创建 UserDTOs**:
    *   **原子操作**: 在 `models/` 目录下创建 `user.ts` 文件。
    *   **逻辑概要**: 定义与前端交互的标准化数据结构，例如：
        *   `UserListItemDto`: 用户列表里每个用户对象应该长什么样。
        *   `UserDetailsDto`: 获取单个用户详情时返回的对象。
        *   `CreateUserDto`: 创建用户时，请求体应该包含哪些字段。
        *   `UpdateUserDto`: 更新用户时，请求体可以包含哪些字段。
    *   **预期结果**: `user.ts` 创建完成，定义了清晰的 API 数据契约。

### **第五步：重构 API 控制层 (Controller)**

1.  **改造 Users API 路由**:
    *   **原子操作**: 修改 `app/api/admin/users/route.ts` 和 `app/api/admin/users/[id]/route.ts`。
    *   **逻辑概要**: 将这两个文件“掏空”，只留下最薄的一层。每个 HTTP 方法 (GET, POST, PUT, DELETE) 的处理函数现在只做几件事：
        1.  从请求中解析出参数。
        2.  调用 `UserService` 中对应的方法处理业务。
        3.  从 `UserService` 拿到结果，用我们定义的 `ApiResponse` 和 `UserDTO` 包装一下，然后返回 `NextResponse.json()`。
        4.  添加全局的错误处理。
    *   **预期结果**: API 路由文件变得非常简洁，只负责调度，不再有业务或数据库逻辑。

### **第六步：前端联动修改**

1.  **调整用户管理页面**:
    *   **原子操作**: 检查并可能修改 `app/admin/users/page.tsx` 以及相关的组件，如 `components/admin/DataTable.tsx` 和 `components/admin/UserForm.tsx`。
    *   **逻辑概要**: 由于后端的返回数据结构可能已经因为 DTO 和 `ApiResponse` 的引入而改变，需要确保前端的 `fetch` 请求后，能正确解析和使用新的数据结构来渲染页面和处理表单。
    *   **预期结果**: 前端用户管理页面功能正常，能够与重构后的后端 API 顺畅通信。
